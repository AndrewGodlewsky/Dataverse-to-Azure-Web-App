# Architecture decisions — 2026-08

## ADR-0001 — Access Dataverse live via the Web API; no copy store

- **Status:** Accepted
- **Date:** 2026-08-08
- **Domain:** Data access
- **Confidence:** Medium
- **Supersedes:** None
- **Superseded by:** None

### Context

The dashboard needs Dataverse data. The options atlas surveyed seven egress paths;
the discriminating platform limits are the 50,000-row aggregate cap and the shared
service-protection throttle bucket (6,000 requests/5-min window for the app's single
application user). The owner assessed that no dashboard chart will need to aggregate
across 50,000+ rows now or plausibly soon, and all viewers may see all data (no
per-viewer security), which removed the strongest remaining arguments for a copy or
hybrid store.

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. Live-only via Web API | $0/mo, <1 day setup, always-current data, one store, Dataverse security applies | 50k aggregate cap and shared throttle bucket are hard ceilings; BFF caching mandatory |
| B. Copy-only (Synapse Link + serverless SQL, deep links for files) | No caps or throttles; one query engine | ~15–45 min staleness everywhere; hierarchy views must be materialized; files need deep links; 1–2 days plumbing for a problem the data doesn't have |
| C. Hybrid (live + copy) | Each workload lands on the store whose limits it fits | Two query paths in the BFF; only justified when the cap actually trips |
| D. Do nothing (no dashboard data source) | — | Defeats the project |

### Decision

The Node BFF reads Dataverse directly through the Web API (OData/FetchXML) using the
S2S application user. No copy store is built. The TDS endpoint is not used by the app
(kept only for ad-hoc human SQL exploration).

**Tradeoff accepted:** every aggregate must stay under the 50k-row cap and all
viewers share one 6k/5-min throttle bucket; the BFF's TTL cache and central
`Retry-After` handling are load-bearing, not optional.

**Tripwire (recorded intent):** if a chart ever needs an aggregate touching ≥50k rows,
or sustained 429 throttling appears, add Azure Synapse Link additively (per the
atlas §3.1 option 3) — this extends the architecture without rebuilding it, and would
be recorded as a superseding ADR.

### Consequences

- **Positive:** zero egress cost; zero data-pipeline build time; data is always
  current; the whole build fits the one-week box with margin.
- **Negative:** dashboard-wide analytics headroom is bounded by platform limits the
  team does not control; a future large table forces the tripwire; cache staleness
  (TTL) is traded for throttle safety.
- **Follow-on work:** implement the BFF TTL cache and 429/`Retry-After` handler as
  first-class components; verify each new chart's aggregate scope at design time.

## ADR-0002 — Stage the S2S credential: client secret first, federated identity credential as end state

- **Status:** Accepted
- **Date:** 2026-08-08
- **Domain:** Auth & identity
- **Confidence:** High
- **Supersedes:** None
- **Superseded by:** None

### Context

The BFF authenticates to Dataverse server-to-server via an Entra app registration
bound to an unlicensed Dataverse application user. Three credential variations were
explored in depth (docs/s2s-credential-variations.md): client secret, federated
identity credential (FIC), and managed identity direct. The application-user binding
is identical for secret and FIC, making a staged path zero-rework; day-1 connectivity
matters because Dataverse queries should run before any Azure infrastructure exists.

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. Staged: secret → FIC | Day-1 laptop connectivity; local dev identical to prod; ends secretless; upgrade is config + ~10 lines | Two IT touches (secret now, FIC later); a secret exists temporarily |
| B. FIC from day 1 | Never any secret | First query blocked on Azure infra provisioning; local dev needs a separate credential from the start |
| C. Managed identity direct | Smallest Entra footprint; no directory operation for IT | Permanent dual-identity local dev (second application user); forecloses delegated/OBO scenarios; different binding — not upgradeable from A |
| D. Do nothing (no S2S identity) | — | The app cannot read Dataverse |

### Decision

Start with an app registration + client secret (12–24 mo expiry) bound to the
Dataverse application user. Once the Web App's user-assigned managed identity exists,
add a federated identity credential to the same registration, switch the BFF token
module to the MI-assertion flow, and delete the secret. Both stages are deliberate;
the application user never changes.

**Tradeoff accepted:** a rotating secret exists during stage 1, and the FIC upgrade
is a second IT interaction that must actually happen (risk: stage 1 quietly becomes
permanent).

### Consequences

- **Positive:** first Dataverse query possible on day 1 from a laptop; production
  ends with zero stored secrets and nothing that expires; per-user (OBO) auth remains
  possible later since the app registration survives.
- **Negative:** until stage 2 completes, secret rotation and leakage are live risks;
  transient `AADSTS70021` after FIC changes requires retry handling.
- **Follow-on work:** schedule the stage-2 upgrade as part of Azure provisioning;
  isolate token acquisition in one BFF module so the swap is contained.

## ADR-0003 — Gate viewers with Easy Auth and an assigned Entra group

- **Status:** Accepted
- **Date:** 2026-08-08
- **Domain:** Auth & identity
- **Confidence:** High
- **Supersedes:** None
- **Superseded by:** None

### Context

Viewers are internal tenant users, access is granted person-by-person, and everyone
granted access may see everything (no per-viewer data restrictions). That rules out
any need for per-user Dataverse security (OBO) and makes viewer-specific responses —
which would defeat the BFF cache ADR-0001 depends on — actively undesirable.

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. Easy Auth + "Assignment required" + viewer group | Zero auth code; platform gates the site before the container; membership managed in one Entra group | Sign-in UX is Microsoft's; authorization granularity stops at the front door |
| B. Easy Auth, any tenant user | Simplest possible | Whole tenant can open the dashboard — contradicts deliberate access granting |
| C. In-app MSAL (+ optional OBO) | Full UX control; per-viewer Dataverse security possible | Days of auth plumbing buying nothing under the no-restrictions model; viewer-specific responses break the shared cache |
| D. No auth | — | Dataverse-derived data on an open URL |

### Decision

App Service Easy Auth with the Microsoft Entra provider gates the entire site;
the auto-created enterprise application is set to **Assignment required** and a
dedicated viewer group is assigned. Granting access = adding a person to the group.
The app contains no sign-in or authorization code; the BFF may read
`X-MS-CLIENT-PRINCIPAL*` headers for display/telemetry only.

**Tradeoff accepted:** all authorization lives at the front door — the app cannot
distinguish viewers, by design.

### Consequences

- **Positive:** minutes of setup; unspoofable identity headers; cacheable (non-viewer-
  specific) responses preserved; access management is a group-membership operation.
- **Negative:** any future per-viewer data filtering requires revisiting this record
  (likely alongside OBO, whose door ADR-0002 keeps open).
- **Follow-on work:** create the viewer group and set Assignment required as part of
  Azure provisioning (IT package item E).

## ADR-0004 — Ship one multi-stage container image via ACR to Web App for Containers

- **Status:** Accepted
- **Date:** 2026-08-08
- **Domain:** Hosting & deployment
- **Confidence:** High
- **Supersedes:** None
- **Superseded by:** None

### Context

The deployment target frame (container image → registry → Azure Web App) was fixed at
project framing. Within it, the structural choices are image shape and registry/pull
architecture. App Service custom containers expose exactly one HTTP port, and the
frontend is a static build with a Node BFF — there is no independent-release pressure
between them.

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. Single multi-stage image (Vite build stage → Node runtime serving /api + static), ACR, managed-identity pull | One deploy unit, one TLS endpoint, no CORS; matches the one-port model; no registry credentials stored anywhere | Frontend and BFF release together |
| B. Separate nginx + Node images (two apps or sidecars) | Independent release cadences | CORS, two apps to manage, more cost/config — unjustified for a one-week internal app |
| C. ACR admin-account pull auth | Portal-flow convenience | Shared username/password, no RBAC, disabled by default, policy-deniable — the documented anti-pattern |
| D. Do nothing (no containerization) | — | Contradicts the fixed project frame |

### Decision

One multi-stage Dockerfile: stage 1 builds the Vite bundle, stage 2 is a slim Node
image (node:22-alpine) running Express, serving `/api` and the static build on the
port named in `WEBSITES_PORT`. The image lives in ACR (Basic tier); the Web App pulls
it with its managed identity holding **AcrPull** (`acrUseManagedIdentityCreds=true`).
Plan tier (currently B1) and CI/CD rung (currently manual) are deliberately *not*
part of this record — both are reversible operational settings.

**Tradeoff accepted:** frontend and BFF version together; a frontend-only tweak
ships a full image.

### Consequences

- **Positive:** single artifact to build, tag, and roll back; no CORS surface; no
  registry credentials exist; ~$17/mo floor at current settings.
- **Negative:** image rebuilds on any change; if independent frontend/BFF release
  cadence ever matters, this record must be superseded.
- **Follow-on work:** set `WEBSITES_PORT`; pick a tag strategy at first deploy
  (`:latest` vs immutable tags) — an operational choice, not an ADR.

## ADR-0005 — Build the frontend as Vite + Express + Apache ECharts

- **Status:** Accepted
- **Date:** 2026-08-08
- **Domain:** Frontend
- **Confidence:** Medium
- **Supersedes:** None
- **Superseded by:** None

### Context

Custom cross-filtering interactivity is the project's founding requirement — it is
why Power BI was ruled out. The data includes hierarchies (org-chart/tree shapes) and
potentially dense series. Three stack combos were compared (atlas §3.5); AG Charts
Community was disqualified (required shapes are Enterprise-paywalled) and visx was
flagged as a one-week-box risk.

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. Vite + Express + ECharts | Only library with every needed shape native (incl. tree); cross-filtering machinery built in; canvas headroom; Apache-2.0 | Options-object API is the least React-ish; largest bundle (mitigated by modular imports) |
| B. Vite + Express + Recharts | Lowest learning curve; JSX-composable | No tree series; cross-filtering hand-rolled — friction exactly on the founding requirement |
| C. Next.js standalone + visx | No ceiling on bespoke visuals | SSR buys nothing for client-rendered charts; highest build cost; week-1 risk |
| D. Do nothing (no charting layer) | — | No dashboard |

### Decision

The frontend is a Vite-built React SPA; the BFF is Express (same container,
ADR-0004); charts are Apache ECharts via echarts-for-react, imported modularly
(`echarts/core`). Cross-filtering uses ECharts' native event/action machinery
(`on`, `dispatchAction`, `connect`).

**Tradeoff accepted:** chart definitions live in ECharts option objects rather than
idiomatic JSX, and the team learns that API.

### Consequences

- **Positive:** every planned shape (KPI/bar/line, treemap, sunburst, tree/org-chart)
  works from one library; interactivity ceiling comfortably above the requirement;
  no license cost or paywall risk.
- **Negative:** bundle size needs active management; the community-maintained React
  wrapper is a (thin) dependency risk — worst case is writing the ~100-line wrapper
  in-house.
- **Follow-on work:** none beyond normal build.

## ADR-0006 — Record architecture decisions as ADRs in plans/architecture/

- **Status:** Accepted
- **Date:** 2026-08-07
- **Domain:** Planning & records
- **Confidence:** High
- **Supersedes:** None
- **Superseded by:** None

### Context

The project accumulates decisions across planning sessions, and the owner asked for
repo-local memory so future sessions inherit them. The repo had no existing decision
location; without one, decisions live only in conversation history and get re-argued.

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. ADR log at plans/architecture/ (record + year index + master index, append-only) | Versioned with the code; reviewable at commit; readable from a bare clone; append-only history preserves when/why direction changed | Three files must move together per record (a post-commit hook nudges) |
| B. Decisions only in HANDOFF/README prose | One file | Overwritten in place — loses the history of changed direction; no options-considered discipline |
| C. Do nothing (conversation memory only) | Zero effort | Decisions evaporate between sessions; re-litigation |

### Decision

Ratified, architecturally significant, hard-to-reverse decisions are recorded as
ADRs under `plans/architecture/` — one decision per record, append-only, indexed in
the year `INDEX.md` and master `DECISIONS.md`, template in `TEMPLATE.md`. Reversible
implementation choices are deliberately excluded. A fail-open post-commit hook
(`.githooks/post-commit`, activated via `core.hooksPath`) prints a one-line reminder
on architecture-adjacent commits lacking a complete ADR update.

**Tradeoff accepted:** recording discipline costs a few minutes per decision, and an
incomplete update (record without indexes) misleads until fixed.

### Consequences

- **Positive:** decisions survive sessions and are reviewable in the PRs that change
  them; rejected options stay visible.
- **Negative:** the log only works if maintained — stale indexes are worse than none.
- **Follow-on work:** none; the hook is active.

## ADR-0007 — Plan large efforts as wayfinder maps on GitHub Issues; keep research assets in-repo

- **Status:** Accepted
- **Date:** 2026-08-07
- **Domain:** Planning & records
- **Confidence:** High
- **Supersedes:** None
- **Superseded by:** None

### Context

The research effort was first charted as a local-markdown wayfinder map
(`wayfinder/map.md` + ticket files). The owner asked to move the tickets to GitHub
Issues so they could be worked one by one — including by parallel agent sessions —
with visible progress. Two parallel stores of the same tickets would drift.

### Options considered

| Option | For | Against |
|--------|-----|---------|
| A. GitHub Issues: map issue + sub-issues, native blocked-by dependencies; research markdown stays in wayfinder/research/ | Frontier visible in GitHub's own UI; sub-issue progress rollup; safe concurrent claiming by assignee; survives outside any one machine | Planning history splits across repo and issue tracker |
| B. Local-markdown tracker (the original) | Everything in one clone; greppable | No visual frontier; concurrent sessions race on file edits; invisible to collaborators |
| C. Both in parallel | — | Guaranteed drift; the failure the migration exists to prevent |

### Decision

Wayfinder planning lives on GitHub Issues: the map is an issue labelled
`wayfinder:map`, tickets are its sub-issues (labels `wayfinder:research|task|…`),
blocking uses native issue dependencies, claiming = assignment, resolution = comment
+ close. Bulky research outputs remain markdown files under `wayfinder/research/`,
linked from their issues. The local map file is a pointer only. A finished effort's
map is closed; **new large efforts chart new maps** rather than reopening closed
ones (the first map, issue #8, is closed with destination reached).

**Tradeoff accepted:** planning context requires GitHub access; issue links into the
repo only resolve once the referenced files are pushed.

### Consequences

- **Positive:** parallel agent sessions worked tickets concurrently without
  collisions (proven in this project); progress legible to any collaborator.
- **Negative:** offline clones see pointers, not the planning detail.
- **Follow-on work:** none for the closed map; apply the pattern to future efforts.
