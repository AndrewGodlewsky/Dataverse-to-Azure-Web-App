Getting the image there, and running

Build in the cloud, not on your laptop

az acr build --registry $ACR --image dashboard:latest .

That single command uploads your source, builds the image inside Azure, and pushes the result into the registry. The trailing . is the build context — the directory whose contents get uploaded. (Build and run with ACR Tasks)

The consequence worth noticing: no Docker Desktop required. On a locked-down corporate Windows machine that is not a convenience, it is the difference between shipping and not. A five-minute build costs about three cents.

What actually gets uploaded

Everything in the context except what .dockerignore excludes. Open yours: it drops node_modules, .git, .env, docs, plans, wayfinder and all markdown. Sensible — and worth checking after you add anything to the repo.

Something you can see for yourself right now

.dockerignore was written before this teaching workspace existed, so learning/ is not excluded — every lesson file would be uploaded on your next build. Harmless (they are not copied into the image) but pointless. Adding one line fixes it, and noticing things like this is exactly the skill the mission is after.

The fact that catches everyone once

You push a new image. You refresh the site. Nothing has changed. Nothing is broken either — App Service pulls the image when the app starts, and your app is already running, so it is still running the old one.

az webapp restart --name $APP --resource-group $RG

That is the whole of rung one from figure 8: build, then restart. The rungs above it exist only to remove that second command — an ACR webhook can restart the app on push, and GitHub Actions can do the whole chain from git push. Your project chose to stay on rung one deliberately while the infrastructure is still moving.

Setting an app setting also restarts the app. So if you change CLIENT_SECRET and the image at the same time, you get the new image as a side effect — which can make it look like the webhook you never configured is working.

Tags, and why :latest is a choice

:latestImmutable tags
Deploy stepRestartUpdate config, then restart
RollbackRebuild the old codePoint at the old tag
"What is running?"Unanswerable from configWritten in the config

:latest is right while you are iterating on infrastructure and wrong once other people depend on the site. Switching later costs one flag on the build and one az webapp config container set.

When it does not come up

The first deploy of any container fails for one of about four reasons, and you find out which by reading the container's own logs:

az webapp log config --name $APP --resource-group $RG --docker-container-logging filesystem
az webapp log tail   --name $APP --resource-group $RG

Leave the tail running and restart the app in another window. You will see the image pull, then the container start, then your own dashboard up on :8080 line. Wherever it stops is your answer:

Log stops atCause
Pulling the imageAcrPull missing, or acrUseManagedIdentityCreds not set
Container started, then site times outPort mismatch — check WEBSITES_PORT
Node crashes immediatelyA missing app setting; read the stack trace
Site loads, /api returns 502Not a deploy problem — that is lesson 06

The blank-page case specifically

A container that starts happily but serves nothing is almost always the port. App Service auto-detects 80 and 8080, and your image exposes 8080 — so this should work even without WEBSITES_PORT. Set it anyway: the App Service FAQ says to for custom containers, and one explicit setting removes a whole class of ambiguity from your next outage.
