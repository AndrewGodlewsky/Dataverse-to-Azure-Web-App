Lesson 07 · The ceilings

The limits that decide the architecture

Three numbers explain the entire options atlas. Two of them are why a copy of your data might ever be worth building, and one of your mission's success criteria is being able to say so with your own row counts.

~40 minutes Pairs with figures 3 and 10 The lesson that lets you defend ADR-0001

Recall from lesson 06: what is _cr_account_value?

The three numbers

LimitValueWhat happens at the edge
Page size5,000 rowsYou get a link to the next page. An inconvenience
Request budget6,000 / 5 min429 with Retry-After. A slowdown, shared by everyone
Aggregate scope50,000 rowsA hard error. No paging around it

The budget has two companions worth knowing: 20 minutes of total execution time and 52 concurrent requests, in the same five-minute window. (Service protection API limits) All three are counted per user — and your app is one user, so every viewer draws from one pot. That single fact is what lesson 03's app-level-versus-per-viewer trade was really about.

Two of the three are already handled — in your code

Paging

In server/dataverse.js:

Prefer: `odata.maxpagesize=${maxPageSize}`
...
url = body["@odata.nextLink"] ?? null;   // loop until there is no next page

Ask for a page size, then follow the link Dataverse hands back until it stops handing one back. (Page results) Ordinary, and the reason lesson 01 insisted this loop belongs on a server.

Throttling

if (res.status === 429 && attempt < 3) {
  const waitSec = Number(res.headers.get("Retry-After")) || 2 ** attempt;
  await new Promise((r) => setTimeout(r, waitSec * 1000));
  return fetchWithRetry(url, token, maxPageSize, fetchImpl, attempt + 1);
}

Dataverse tells you how long to wait; the code waits that long, falling back to exponential backoff if the header is missing, and gives up after three tries. Notice where this lives: in one function that every query goes through. Throttle handling scattered across callers is how you get an app that half-works under load.

The third one is not handled, on purpose

There is no code for the aggregate cap, because this app never asks Dataverse to aggregate. Look at what provider.js actually does: it fetches order rows and sums them in JavaScript.

export function summarize(orders, category) {
  const rows = category ? orders.filter((o) => o.category === category) : orders;
  return { totalRevenue: Math.round(rows.reduce((s, o) => s + o.total, 0)), ... };
}

That is a deliberate trade, and you should be able to state both halves:

Aggregating in the BFF (chosen)Aggregating in Dataverse
Never near the 50,000-row capHits the cap the moment a groupby scans 50k
Cross-filtering is free — filter in memoryEvery filter is a new upstream query
Pulls every row, every cache expiryPulls only the answer
Fine at thousands of rowsFine at any row count it can answer

So the design is right for a table of thousands and wrong for a table of millions. Which yours is, nobody has ever checked.

The tripwire — this is the thing to remember

ADR-0001 chose live-only with a condition attached: if an aggregate needs ≥50,000 rows, or 429s become sustained rather than occasional, the copy branch opens — additively, alongside the live leg, with a superseding ADR. That is not a failure of the design; it is the design's own stated exit.

You are the person who will notice it firing. Nobody else is watching.

How to know where you stand

  1. Count the rows. In the maker portal, or with ?$count=true&$top=1 on your orders entity set. Under ~50,000 total, the current design is comfortable. Approaching it, start planning.
  2. Watch for 429s. They surface as slow loads, not errors, because the retry hides them. Add a console.warn in the retry branch and you will see them in az webapp log tail.
  3. Count the fan-out. Five charts on load, refetching on every filter click — but the TTL cache collapses those to one upstream call per key per minute. Raise CACHE_TTL_SECONDS before you do anything more drastic.

The cache is the cheapest lever you own. server/cache.js stores the promise, not just the value, so ten simultaneous viewers on a cold cache share one upstream request rather than starting ten.

Do this now

  1. Get the real row count of your orders table. Write it down.
  2. Answer, in one sentence with that number in it: "we read live rather than copying because…". That sentence is a success criterion of your mission.
  3. Now answer the harder one: "and we would revisit that if…" — the tripwire, in your own words, with your own numbers.
  4. Add a console.warn in the 429 branch of server/dataverse.js. One line, and it turns an invisible condition into a visible one.
