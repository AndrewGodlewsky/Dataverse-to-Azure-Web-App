Lesson 04 · Provisioning

Making the Azure side exist

Five commands create everything. The mission says you should be able to explain every flag you typed — so this lesson is the five commands with nothing waved through.

~45 minutes Needs a subscription with Contributor Pairs with figure 7

Recall from lesson 03: authentication required, no assignment — who gets in?

Four words of vocabulary first

  • SubscriptionThe billing boundary. Everything you create belongs to exactly one, and its owner gets the invoice.
  • Resource groupA folder with a lifecycle. Resources in it can be listed, permissioned, and — importantly — deleted together. Put this whole project in one, and cleaning up is a single command.
  • RegionWhich datacentre. Pick one near your users and keep everything in it; cross-region traffic costs money and latency.
  • ResourceAny single thing you create — a registry, a plan, a web app. Some names are unique globally, not just in your account, because they become public DNS.

The five commands

Names first. Choose them now and reuse them consistently; two of the three must be globally unique, so add something distinctive.

$RG   = "rg-dashboard"          # yours alone, any name
$ACR  = "acrdashboard1234"      # GLOBAL: letters+digits only, 5-50 chars
$PLAN = "plan-dashboard"        # yours alone
$APP  = "dashboard-yourorg"     # GLOBAL: becomes dashboard-yourorg.azurewebsites.net
$LOC  = "eastus"

1 — The folder

az group create --name $RG --location $LOC

--location here sets the region for the group's own metadata; each resource still takes its own location. Costs nothing — a group is free.

2 — The registry

az acr create --resource-group $RG --name $ACR --sku Basic

--sku Basic is the $5/month tier: 10 GiB and two webhooks, with the same authentication and RBAC as the expensive tiers. The only thing you would move up for is private endpoints (Premium, +$45). Billing starts now, not when you first push.

3 — The plan

az appservice plan create --name $PLAN --resource-group $RG --is-linux --sku B1

The plan is the rented hardware; the web app is a site running on it. This is the line that costs $12.41/month, and it charges whether or not anything is deployed. --is-linux is not optional for a Linux container — omit it and you get a Windows plan that will refuse your image.

One plan can host several web apps. That is the cheap way to add a staging site later — not a second plan.

4 — The web app

az webapp create --resource-group $RG --plan $PLAN --name $APP `
  --container-image-name "$ACR.azurecr.io/dashboard:latest"

The image does not exist yet — that is fine. You are declaring what it will run; lesson 05 puts the image there.

A flag you will see in every blog post — and should not copy

Older examples use --deployment-container-image-name. The CLI reference now marks it Deprecated; the current flag is --container-image-name (-c). (az webapp config container) When you find a tutorial, check its flags against the CLI reference before pasting.

5 — Identity, and the right to pull

az webapp identity assign --resource-group $RG --name $APP

az role assignment create `
  --assignee $(az webapp identity show -g $RG -n $APP --query principalId -o tsv) `
  --scope    $(az acr show -g $RG -n $ACR --query id -o tsv) `
  --role     AcrPull

az resource update --ids $(az webapp config show -g $RG -n $APP --query id -o tsv) `
  --set properties.acrUseManagedIdentityCreds=true

Three steps, three ideas:

  1. Give the app an identity. A managed identity is an Entra identity that Azure creates, rotates and destroys with the resource. There is no secret, because the platform vouches for the app directly. (Managed identities in App Service)
  2. Grant it a role somewhere. Every Azure permission is this shape: who (assignee) gets what (role) where (scope). AcrPull on the registry — read the images, nothing else, nowhere else.
  3. Tell App Service to use it. Without acrUseManagedIdentityCreds the platform keeps looking for a registry username and password, and the pull fails with an unauthorised error that says nothing about identity.

Settings the app will need

Environment variables on Azure are called app settings. They are injected into the container at start.

az webapp config appsettings set -g $RG -n $APP --settings `
  WEBSITES_PORT=8080 `
  DATAVERSE_URL="https://yourorg.crm.dynamics.com" `
  TENANT_ID="..." CLIENT_ID="..." CLIENT_SECRET="..."

You met all five in earlier lessons: one port rule (lesson 01) and four credential values (lesson 02). Setting app settings restarts the app — which will matter in lesson 05.

Order is not arbitrary

Plan before web app (the app needs somewhere to run). Registry before role assignment (you cannot scope a role to a thing that does not exist). Identity before role assignment (there is no assignee otherwise). Everything else is free order.

Do this now — even without a subscription

  1. Open a scratch file and write the five commands out with your chosen names filled in. Do not run them yet if you are not ready to be billed.
  2. Beside each flag, write one clause saying what it does. If any clause is "not sure", that is your next question for me.
  3. Run az account show. If it errors, you need az login first — do that now so it is not a surprise later.
  4. Write the teardown command underneath. Knowing you can delete everything in one line is what makes it comfortable to create it.
