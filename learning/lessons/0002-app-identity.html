Lesson 02 · App identity

How the app proves it may read

Three separate objects have to exist before a single row comes back, and they live in two different admin portals. Most first-time S2S failures are one of the three simply missing.

~40 minutes Builds on lesson 01, hop 6 Pairs with figure 5

Recall from lesson 01: which part holds the Dataverse credential?

Three objects, two portals

Hop 6 of the trace was one sentence: "the BFF presents the app's own credential and gets a token." Underneath, that requires three things to exist. Keep them distinct — people conflate them constantly, and the error messages will not help you.

  • Lives in Entra ID (Azure portal) 1 · The app registration An identity for a piece of software, the way a user account is an identity for a person. It gets an Application (client) ID and a credential. That is all it is: proof of who is calling. It grants no access to anything.
  • Lives in Dataverse (Power Platform admin center) 2 · The application user An account inside your Dataverse environment that is bound to that Application ID. This is the moment Dataverse agrees the registration is someone it knows. It consumes no licence.
  • Lives in Dataverse 3 · The security role What that application user may do — here, Read on a named list of tables and nothing else. Assigned to the application user from object 2.

Identity, account, permission. One in Azure, two in Power Platform. If you remember nothing else from this lesson, remember that the app registration by itself opens no doors at all.

The surprising part: no API permissions

If you have ever registered an app before, you will expect to add API permissions and click "Grant admin consent". For this pattern you do not. Microsoft's documentation is explicit: "If your app uses Server-to-Server (S2S) authentication, you don't need to complete this step." (Use OAuth with Dataverse)

The reason is the whole design: authorization does not come from Entra here. It comes from the binding in object 2 plus the role in object 3. Entra answers only "is this really that app?" Dataverse answers "and what may it read?"

This is why the IT ask is small. You are not requesting access to a Microsoft API — you are requesting an identity, and then your own Dataverse admin decides what it can see.

What this means when IT pushes back

A security reviewer asking "what permissions does this app registration have?" can be told, truthfully: none. It has no delegated or application permissions to any API. Its only power is whatever the Dataverse security role grants, which is Read on a listed set of tables, revocable in the admin center without touching Azure.

The token, in your own code

Open server/dataverse.js. The whole of hop 6 is this:

cca ??= new ConfidentialClientApplication({
  auth: {
    clientId: CLIENT_ID,
    authority: `https://login.microsoftonline.com/${TENANT_ID}`,
    clientSecret: CLIENT_SECRET,
  },
});
const result = await cca.acquireTokenByClientCredential({
  scopes: [`${DATAVERSE_URL}/.default`],
});

Read it as a sentence: "I am CLIENT_ID, in directory TENANT_ID, and here is my CLIENT_SECRET as proof. Give me a token for DATAVERSE_URL." That is the client credentials flow — the OAuth flow for software acting as itself, with no human involved. (MSAL Node — acquire token)

So your four environment variables are not four arbitrary settings. Three of them are the sentence above, and the fourth is the address:

VariableAnswersWhere IT gets it
TENANT_IDWhich directory?Directory (tenant) ID on the registration
CLIENT_IDWhich app?Application (client) ID on the registration
CLIENT_SECRETProve itCertificates & secrets → New client secret
DATAVERSE_URLToken for what, and call where?Your environment's URL

Note that DATAVERSE_URL does double duty: it becomes the scope (.../.default means "every permission this app already has for that resource") and the base of every request URL.

The credential ladder — and why yours is rung one

A shared secret string is the fastest credential and the weakest. There are four rungs, and figure 5 draws all of them. The important structural fact: the three objects above are identical on every rung. Only what the app presents changes.

RungSecret exists?Setup
Client secretYes — expires in 1–2 yearsMinutes

Federated credentialNo — registration trusts the Web AppHours

Your project deliberately starts at rung one and plans to end at rung four (ADR-0002), because rungs three and four need a Web App that does not exist yet. The code was written for that: the swap replaces getToken() and nothing else. You will do it in lesson 09.

The gotcha that produces silent wrong data

If any dashboard column is column-secured in Dataverse — a salary, a credit limit — a valid token and a correct security role are still not enough. The application user must also be added to a column security profile, or those columns come back masked rather than erroring. (Column-level security) A chart of masked values looks like a data problem, not a permissions problem. That is what makes it expensive.
