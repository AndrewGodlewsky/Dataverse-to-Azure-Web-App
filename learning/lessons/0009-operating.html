Diagnose by bisecting the trace

You have known the seven hops since lesson 01. Debugging is just asking which hop is the last one that works. Four questions, in order, and each one eliminates half the system:

  1. Does the container start? az webapp log tail, then restart. If you never see dashboard up on :8080, stop here — nothing downstream matters. Pull failure or crash on boot.
  2. Does the site respond at all? Open it in a private window. Challenged to sign in → the gate works. Blank page with a healthy container → port. No challenge at all → lesson 03's switches.
  3. Does /api/meta answer? The cheapest possible probe — it returns the mode and touches no credential. Answers "live"? Your env vars are present. Answers "mock" in production? An app setting is missing.
  4. Do the data routes answer? A 502 here means the upstream query failed: token, role, or table name. The container log has the real error; the browser only ever sees upstream query failed.

Why /api/meta is the probe worth remembering

It splits the system exactly in half. Everything before it is Azure — image, port, gate, settings. Everything after it is Dataverse — token, role, columns. One request tells you which half to think about, and it never fails for credential reasons.

The reference card has the full symptom-to-suspect table. Print it. The point of a printed card is that you reach for it when the thing you would normally search on is the thing that is down.

Notice the pattern: the status code names the object. 401 is identity, 403 is permission, 404 is the table, 400 is the column. Four numbers, four of the things you built.

Deleting the secret

Right now there is exactly one password in this system: CLIENT_SECRET, sitting in an app setting, expiring in a year or two. ADR-0002 always intended it to be temporary — rung one of the ladder from lesson 02, with rung four as the destination. Now that the Web App exists, you can climb.

  1. Create a user-assigned managed identity and attach it to the Web App. It must be user-assigned — only those can back a federated credential. (Configure an app to trust a managed identity)
  2. Add a federated credential on the existing app registration: Certificates & secrets → Federated credentials → scenario Managed Identity → select the identity from step 1. Audience api://AzureADTokenExchange.
  3. Swap getToken() in server/dataverse.js — the identity asks for a token, the registration accepts it as an assertion. The comment at the top of that file says this is the only function that changes, and it is true.
  4. Deploy, verify, then delete the secret — in that order. Remove the app setting and the secret on the registration only once live traffic is working without them.

The gotcha that makes step 2 look broken

Federated credential changes take a few minutes to propagate. Until they do you get AADSTS70021 — "no matching federated identity record found" — which reads exactly like a misconfiguration. Wait, retry, and only then start changing things. Doing it in the other order is how people end up with three half-configured credentials.

What you gain: nothing expires, nothing can leak, and the security question "where is the credential stored?" gets the best possible answer — nowhere.
