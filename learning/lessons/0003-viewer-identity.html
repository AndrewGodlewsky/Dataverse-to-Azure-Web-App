Lesson 03 · Viewer identity

How your colleagues get in

The viewer side is three switches in a portal and no code at all. The danger is that two of the three default to something more open than you want, and the app will look perfectly fine either way.

~30 minutes Builds on lesson 01, hop 2 Pairs with figure 6

Recall from lesson 02: how many API permissions does the registration need?

A gate, not a login page

Easy Auth is App Service's built-in authentication. Switching it on puts a gate in front of your container: any request without a valid session is redirected to Entra ID to sign in, and only comes back once it has one. Your code never sees an anonymous request and contains no auth logic whatsoever. (Authentication and authorization in App Service)

This is the reason lesson 01 called it a feature rather than a part. It is a checkbox on the Web App you will create in lesson 04, not a thing you build.

Three switches, and what each one actually decides

SwitchWhereIf you skip it
Add identity provider → Microsoft Web App → Authentication The site is fully public on the internet

Assignment required + assign a group Entra → Enterprise applications Every user in your tenant can sign in

The third switch is the one people miss

With the first two set, the gate is closed to the internet — and wide open to your entire organisation. "Signed in with a work account" is not the same as "allowed to see this dashboard". The tightening step lives in a different portal blade (Enterprise applications, not App registrations), which is exactly why it gets skipped.

Your project decided on assignment required plus a named viewer group (ADR-0003). Until that group exists and is assigned, treat the dashboard as company-wide.

What the container is told about the viewer

Once someone is through, App Service injects headers describing them — X-MS-CLIENT-PRINCIPAL-NAME, X-MS-CLIENT-PRINCIPAL-ID, and a fuller encoded principal. (Work with user identities) They are trustworthy because the platform sets them after stripping anything the caller sent, so a browser cannot forge them.

Now go looking for those headers in your code. You will not find them — and that is correct. This dashboard never asks who you are, because everyone who gets in sees the same numbers. If you ever add "your team's orders only", this is the header you would read, and lesson 07's throttle discussion is where the consequences show up.

Add a /api/whoami route that echoes X-MS-CLIENT-PRINCIPAL-NAME and you have a two-line diagnostic for "is the gate actually on?" — useful the first time a deploy behaves oddly.

The road not taken, and why it matters anyway

The alternative is on-behalf-of: the BFF exchanges the viewer's own token for a Dataverse token, so each person reads as themselves. Figure 6 draws both side by side. The trade is worth being able to recite:

App-level (yours)Per-viewer (OBO)
Dataverse securityYou re-implement any rules in codeEnforced natively per person
Throttle budgetOne bucket shared by everyoneOne bucket each
CachingTrivial — responses are identicalHard — every response differs
IT footprintOne application userA security role per viewer
SetupMinutesDays

Read that table as a single sentence: you traded per-person security for a cache. That is a defensible trade for an internal dashboard where everyone is allowed to see everything, and an indefensible one the moment they are not. If the requirement ever changes, this is the decision that has to be reopened — not the code.

Locally, none of this exists

Easy Auth is a property of App Service. On localhost:8080 there is no gate, no sign-in, and no headers. That is expected, not a bug — but it does mean "it worked locally" tells you nothing about whether the gate is configured. The first time you deploy, open the site in a private browsing window: if you are not challenged to sign in, one of the three switches is off.

Do this now

  1. Search the whole repo for X-MS-CLIENT. Confirm it appears nowhere, and be able to say why that is the correct state for this app.
  2. Open figure 6 in docs/options-diagrams.html. Cover the right-hand panel and explain the left one out loud; then swap.
  3. Write down the name of the Entra group that should hold your viewers. If it does not exist yet, that is an item for the same IT conversation as lesson 02 — atlas §6.1 item E.
  4. Decide now, and write it in one line: who is allowed to see this dashboard? You will hand that sentence to whoever creates the group.
