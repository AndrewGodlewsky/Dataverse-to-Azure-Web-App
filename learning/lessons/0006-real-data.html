Lesson 06 · Real data

Pointing it at real tables

This is the moment the design meets reality. Four values switch the app to live, and then two marked edits decide whether it returns your data or an error — and the hard part is not the code, it is finding what your columns are really called.

~45 minutes Needs the four credential values Runs entirely on localhost

Recall from lesson 05: a new image is pushed. What happens to the running site?

The switch is one line

At the bottom of server/provider.js:

export const provider = dv.isConfigured() ? live : mock;

And isConfigured() is just "are all four environment variables present?" So: no .env, mock data. A .env with all four values, live Dataverse. Nothing else in the app knows which happened — the routes call provider.summary() either way.

Do this locally first. Copy .env.example to .env, fill the four values from lesson 02, run npm run dev. The header badge flips from mock to live, and you will almost certainly get a 502 from /api — because the table names in the code are invented. That is the expected next problem.

Reading OData well enough

The Dataverse Web API speaks OData v4. (Web API overview) You only need five facts to read the query in your own code:

ThingLooks likeNote
Entity setcr_ordersThe plural logical name — this is the URL segment
Columncr_totalLogical name, lower-case, publisher-prefixed
Lookup column_cr_account_valueUnderscore prefix and _value suffix. Trips everyone once
Choice columnstatuscodeComes back as a number, not a label
Projection?$select=a,b,cAlways select — never fetch columns you will not use

Now the query in provider.js reads plainly:

"cr_orders?$select=cr_category,cr_orderdate,cr_total,_cr_account_value,statuscode"

From the orders table, give me five columns. That is all it is.

Finding what yours are really called

The display name in the UI is not the logical name in the API. "Order Total" might be cr_total, new_ordertotal or something a consultant chose in 2019. Two reliable ways to find out:

  1. The maker portal. make.powerapps.com → your environment → Tables → your table → Columns. The Name column is the logical name. The table's own plural name is on its properties.
  2. Ask the API. With the app running live, hit <your-url>/api/data/v9.2/$metadata in a browser signed in to Dataverse — the entity sets and every property are listed exactly as the API will accept them.
Write the names down in a scratch file as you find them. You will need the same list for the security role in lesson 02's item C — IT cannot grant Read on tables you have not named.

The two edits

Search server/provider.js for <EDIT>. There are four markers in two places.

Edit one — the orders query and its mapping

const rows = await dv.query(
  "cr_orders?$select=cr_category,cr_orderdate,cr_total,_cr_account_value,statuscode"
);
return rows.map((r) => ({
  category:  r.cr_category ?? "Uncategorized",
  month:     (r.cr_orderdate ?? "").slice(0, 7),
  total:     r.cr_total ?? 0,
  accountId: r._cr_account_value,
  open:      r.statuscode === 1,
}));

Replace the table and column names on both sides. The left-hand names must not change — category, month, total, accountId, open are the shape the rest of the app agrees on. The mock provider produces the same five keys, which is precisely why the charts do not care which one answered.

Two traps in five lines

.slice(0, 7) takes "2026-08" from an ISO date. If your date column is a Date Only column it still arrives as a string — fine. If it is null, the empty string produces an empty month bucket rather than crashing, which is why the ?? is there.

statuscode === 1 is a guess. Choice values are per-table and per environment; "Active" is often 1, but yours might be 100000000. Check in the maker portal before trusting the "open orders" number — it will be wrong silently, not loudly.

Edit two — the org tree

The second query fetches org units and builds a tree from a parent lookup. Same job: replace cr_orgunits, cr_name, cr_orgunitid and _cr_parent_value with yours. If you have no hierarchy table, the code already degrades to a "No org data" node — delete the chart instead of inventing one.

What "live" costs you that mock did not

Every live call now spends from a shared budget and can be throttled, and the whole orders table is fetched to build the aggregates. That is deliberate, and it is the entire subject of lesson 07 — including how to tell whether your real row counts make it a reasonable choice or a broken one.

Retrieval practice

What kind of column is _cr_account_value?

Do this now

  1. In the maker portal, write down the logical names for your order-like table: the entity set, the category, date, amount, account lookup and status columns.
  2. Check what your "open" status value actually is. Write the number down.
  3. Copy .env.example to .env, fill the four values, and run npm run dev. Confirm the badge says live before touching anything else — that proves lesson 02's three objects are all in place.
  4. Make edit one. Refresh. When a chart draws real numbers, you have completed the entire left half of figure 1 on your own.
  5. Run npm test. It exercises the mock path, so it should still pass — if it does not, your edit broke the shared shape.
