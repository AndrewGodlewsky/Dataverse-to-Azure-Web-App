Lesson 01 · The frame

Five parts and one request

You cannot operate a system you cannot name. Before any choice in the options atlas means anything, you need the skeleton those choices hang off — and the path a single click takes through it.

~35 minutes Assumes nothing about Azure or Dataverse Pairs with figure 1 of the diagrams

Why this one first

Your mission is to run this thing yourself: provision it, deploy it, and diagnose it when a colleague says "the dashboard is blank." Every one of those tasks is really the same task — knowing which part broke. That requires a frame with named parts, which is what this lesson builds. Every later lesson changes exactly one part of it.

The five parts

Here is the whole system. Notice how few pieces there are — the complexity in the atlas comes from the choices at each part, not from the number of parts.

  • Microsoft runs it · your company's data Dataverse The database your business already keeps its rows in — but more than a database: it also carries a security model (who may read which table, which column) and a web API. It is the system of record. Nothing you build owns this data; you are a reader of it. Without it: the dashboard has nothing to draw.
  • You build it The container image A frozen, complete filesystem holding two things at once: the compiled React files a browser will run, and the Node server that hands them over and answers /api calls. One artifact, built once, run anywhere. Without it: nothing to deploy — just source code on your laptop.
  • Azure runs it · you own it Azure Container Registry (ACR) A private shelf that stores your image so Azure can fetch it. Roughly $5/month at the Basic tier. Think of it as the warehouse between "built" and "running". Without it: the Web App has no image to pull.
  • Azure runs it Azure Web App for Containers The managed machine that downloads your image and runs it, handles HTTPS for you, and gives you a public URL. Its price is the plan underneath it — B1 is about $12.41/month. This is also where the sign-in gate lives (next part). Without it: the image sits in the registry, running nowhere.
  • Microsoft runs it · your tenant Microsoft Entra ID Your organisation's identity system — the thing behind every Microsoft 365 sign-in you already do. It issues proof-of-identity in both directions here: it proves your colleagues are who they say they are, and separately it proves your app is who it says it is. Without it: no way to keep strangers out, and no way for the app to convince Dataverse to answer.

Easy Auth is not a sixth part. It is a feature you switch on inside the Web App: a sign-in gate that sits in front of your container, so unauthenticated requests never reach your code at all. (Authentication and authorization in App Service)

The rule that shapes everything: one port

Here is the single platform constraint that explains why your React app and your Node server ship as one image rather than two. Microsoft's documentation states it plainly:

From the App Service docs

"App Service currently allows your container to expose only one port for HTTP requests." (Configure a custom container for App Service)

One port means one thing answering the door. So the Node server answers everything: it serves the React files and the /api routes, from the same origin. A pleasant side effect — because the page and the API share an origin, there is no CORS to configure, ever.

Open your Dockerfile and you can see this rule as architecture. Two FROM lines: the first builds the React bundle, the second is a slim runtime that copies that bundle in and starts Node. Two stages, one image. (Docker multi-stage builds)

A comment in your repo is wrong — and this is how you'd know

server/index.js says // App Service sets WEBSITES_PORT→PORT for containers. The docs say otherwise: WEBSITES_PORT "isn't injected into the container as an environment variable" — it only tells App Service which port to forward to. (App settings reference)

The code still works, because it falls back to 8080 — which is exactly the port WEBSITES_PORT will point at. Right behaviour, wrong reason. This is the whole skill in miniature: read the primary source, not the comment.

The word for the middle: BFF

Your Node server is called a BFF — backend for frontend. It is a server whose only customer is your own web page. It exists here for three specific reasons, and each is worth holding onto:

  1. It holds the secret. Talking to Dataverse requires a credential. Anything shipped to a browser is readable by anyone who opens dev tools, so the credential can only live on a server.
  2. It collapses many viewers into one. All your viewers share a single Dataverse request budget — 6,000 requests per 5 minutes. (Service protection API limits) The BFF caches, so ten people looking at the same chart cost one upstream call, not ten.
  3. It does the paging. Dataverse returns at most 5,000 rows per page and hands back a link for the next one. (Page results) That loop belongs on a server, not in a browser.

Trace one request

A colleague opens the dashboard URL and clicks a bar. Here is every hop. Read it once, then do the ordering exercise below without looking.

  1. Browser → App Service front end The URL resolves to Azure's front end, which terminates HTTPS for you. Your container never handles certificates.
  2. Easy Auth intercepts — before your code No session? The viewer is redirected to Entra ID, signs in with their work account, and comes back with a session cookie. Your container has still not seen a single request.
  3. App Service forwards to the one port Now the request reaches your container, on the single port it listens on. Easy Auth attaches headers describing who the viewer is.
  4. Node serves the app shell HTML and the JavaScript bundle go back. The page renders chart frames with no data in them yet.
  5. Browser calls /api/... — same origin The React code asks its own server for data. Same host, so no CORS. This request arrives at Node just like the last one.
  6. BFF checks cache, then asks Entra for a token On a cache miss the BFF presents the app's own credential to Entra ID and receives a bearer token good for Dataverse.
  7. BFF calls Dataverse; Dataverse checks the role Dataverse looks at what that app identity is allowed to read, returns rows, and the BFF shapes, caches, and returns JSON. ECharts draws.

Now notice what never happened. The browser never contacted Dataverse. Not once, on any option in the atlas. That single fact is the reason the BFF exists, and the reason the credential is safe.

Two identities, endlessly confused

Retrieval practice

Answer from memory. Getting one wrong here is worth more than getting it right after scrolling up — the effort is what makes it stick.

How many ports may your container expose for HTTP on App Service?

Which part holds the credential that Dataverse trusts?

Where does the Easy Auth gate sit relative to your container?

How often does the browser query Dataverse directly?

Why does the BFF cache instead of just proxying?

Do this now — 10 minutes in the real repo

Find all five parts in your own code

  1. Open Dockerfile. Find the two FROM lines. Which one produces files the browser will run, and which one produces the thing that gets deployed?
  2. Open server/index.js. Find the line that chooses a port. Note the fallback value — and now you know why it is that number.
  3. In the same file, find the line that serves static files and the line that mounts /api. That is the one-port rule expressed in eight words of code.
  4. Open server/dataverse.js and find getToken(). That function is hop 6 of the trace. Everything about lesson 02 happens inside it.
  5. Run npm start and open http://localhost:8080. The app runs in mock mode — no Azure, no Dataverse, no credential. Find where the page tells you it is mocked.

Then tell me one thing that surprised you. That answer is how I pick lesson 02's starting point.
