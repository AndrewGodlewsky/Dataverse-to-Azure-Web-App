Changing what the dashboard shows

Cross-filtering is the founding requirement — the reason a custom app exists at all rather than a canned report. It turns out to be about fifteen lines of code, and knowing which fifteen is what lets you change the dashboard safely.

The whole cross-filter loop

In client/src/App.jsx, three fragments do all of it:

const [category, setCategory] = useState(null);
const qs = category ? `?category=${encodeURIComponent(category)}` : "";

const summary = useJson(`/api/summary${qs}`);
const revenue = useJson(`/api/revenue-by-month${qs}`);

onEvents={{
  click: ({ dataIndex }) => {
    const next = catTotals[dataIndex]?.category ?? null;
    setCategory((cur) => (cur === next ? null : next));
  },
}}

Read it as a chain: a click sets state → the state changes a URL → the URL change refetches → the charts redraw. The toggle in the middle (cur === next ? null : next) is what makes clicking the same bar twice clear the filter, which users expect without being told.

An accuracy correction, and it matters

Figure 9 of the diagrams says the filter loop stays in the browser with no server round trip. That describes what cross-filtering can be; it is not what this app does. Here, filtering changes the URL, so the filtered views refetch from the BFF — where the TTL cache usually answers immediately. The two charts that do not take qs (category totals, org tree) genuinely never refetch.

Practical consequence: your cache TTL is part of your interaction latency, not just your throttle protection.

Why it was built this way

The alternative — fetch every row once and filter in memory — would make clicks instant and cost more memory and a bigger first load. Both are defensible. The current choice keeps the browser thin and leans on the cache, which suits an internal dashboard where the first load matters more than the fiftieth click.

ECharts is configured, not composed

Most React chart libraries give you JSX components. ECharts gives you one component and a large plain object.

const revenueOption = revenue && {
  grid:    { left: 48, right: 16, top: 16, bottom: 28 },
  tooltip: { trigger: "axis", axisPointer: { type: "cross" } },
  xAxis:   { ... }, yAxis: { ... }, series: [ ... ],
};

That object is the chart. To change a chart you change the object — nothing else. It is less React-ish than the alternatives and it is why ECharts was chosen: it is the only library that covers every shape this project needs natively, including the tree diagram, with cross-chart interaction built in. (ECharts events)

The wrapper in client/src/EChart.jsx is deliberately tiny — it passes option and onEvents straight through, with notMerge set so a new option replaces the old one rather than being deep merged into it. That last flag prevents a whole category of "the old series is still there" bugs.

Colour comes from CSS, always

const cs = getComputedStyle(document.documentElement);
return Object.fromEntries(ROLE_VARS.map((v) => [v, cs.getPropertyValue(`--${v}`).trim()]));

usePalette() reads CSS custom properties defined in client/src/styles.css and hands them to the chart options. Light and dark are defined once, in CSS, and every chart follows.

The rule to keep

Never hardcode a hex value in a chart option. The moment you do, that series stops following the theme and looks broken in one of the two modes — and nobody will notice until a colleague with dark mode opens it.

Making a change safely

Three changes in increasing order of risk, all in mock mode with no Azure involved:

  1. Cosmetic — adjust a palette variable in styles.css. Every chart updates. No JavaScript touched.
  2. Additive — add a KPI tile. It needs a number from summarize() in provider.js (server) and a tile in App.jsx (client). Note that this crosses the BFF boundary: the shape contract from lesson 06 has to grow at both ends.
  3. Structural — make a second chart clickable. Add onEvents to it and decide what its click means. This is where you can genuinely confuse users: two filters that both exist need a rule for how they combine, and that rule belongs in the state, not in the charts.

Do this now — mock mode, nothing can break

  1. Run the app and click a category bar. Watch the network tab: count how many requests fire, and note which two charts do not refetch.
  2. Change one palette variable in client/src/styles.css. Confirm every chart follows without touching a chart option.
  3. Set CACHE_TTL_SECONDS=1 and click around; then try 600. You are feeling lesson 07's lever from the user's side.
  4. Optional, and the real test: add one KPI tile end to end. If you can do that unaided, you can maintain this dashboard.
