Live vs copy — every way out of Dataverse

The single biggest fork in the whole architecture: query Dataverse live on every request, or maintain an exported copy and query that. Seven viable paths were surveyed; the choice turns on two hard platform ceilings, not on feature preference.

Decision — ADR-0001 (Accepted, medium confidence) The Node BFF reads Dataverse live through the Web API (OData/FetchXML) using the S2S application user. No copy store is built. Grounds: no dashboard chart needs a ≥50k-row aggregate now or plausibly soon, all viewers may see all data, and live costs $0 with <1 day of setup. The BFF's TTL cache and central Retry-After handling are load-bearing consequences of this choice, not optimizations.

The two ceilings that decide everything

These are Dataverse platform limits the team does not control. Every path below is really a position relative to these two numbers — exceeding them isn't a cost, it's an outage.

50,000 rows

The aggregate cap. Any single aggregate query touching ≥50k rows hard-errors — it doesn't slow down, it fails. Global KPIs over large tables are the classic trigger.

6,000 req / 5 min

The service-protection throttle — plus 20 min compute and 52 concurrent calls per window — measured per user. The BFF's single application user is one bucket shared by every viewer, which is why caching must live in the BFF.

The seven paths

Two live, five copy. Setup time and monthly cost are the headline numbers; the limits column is what disqualifies a path for a given workload.

1 · Dataverse Web API (OData v4) — live

Chosen

< 1 day setup · $0/month

Real-time data, smallest setup of any path, Dataverse security applies per query, and FetchXML brings hierarchy operators (Under/Above) nothing else has.

Limits: 5,000 rows/page with no $skip (paging is @odata.nextLink loops), the 50k aggregate cap, and the shared throttle bucket. All three are handled centrally in the BFF.

2 · TDS / SQL endpoint — live

Kept — for humans only

< 1 day setup · $0/month

Real T-SQL SELECT/JOIN/GROUP BY over live data from any SQL client; on by default.

Limits: read-only subset — no CTEs, PIVOT, or OVER; 5-minute query timeout; no elastic tables, no file/image columns; and the same throttles and aggregate cap as the Web API. The app doesn't use it; it stays available for ad-hoc human SQL exploration.

3 · Synapse Link — CSV + serverless SQL — copy

The tripwire path

1–2 days setup · ~$1–20/month (ADLS ~$0.02/GB-mo + $5/TB scanned)

Push-based, near-real-time (15–45 min typical), no aggregate caps, reads never touch Dataverse throttles, full T-SQL. This is the pre-selected escape hatch: if the tripwire fires, this gets added additively and recorded as a superseding ADR.

Limits: needs ADLS Gen2 + change tracking per table; append-only mode forces dedupe logic (VersionNumber, isDeleted=0) into every consumer; Dataverse security roles do not flow to the lake — storage RBAC becomes the boundary; creation needs a Dataverse System Administrator.

4 · Synapse Link — Delta Lake + Spark — copy

Not chosen

2–4 days setup · tens to low hundreds $/month (Spark vCore-hours)

Compressed Parquet (⅓–⅛ the size), faster queries, chooseable sync interval, no dedupe burden (Delta handles it).

Limits: Spark pool provisioning and tuning time; the cost floor rises as the sync interval shortens; same change-tracking and RBAC caveats as #3. The setup time alone crowds a one-week build.

5 · Fabric Link — copy

Not chosen — flagged expensive

Hours if capacity exists · ~$263+/month (F2 24×7) + Dataverse storage draw

Genuinely zero-ETL: a wizard auto-creates Lakehouse + SQL endpoint + semantic model; no storage account to run; the full Fabric surface afterwards.

Limits: the highest fixed cost floor in the atlas, billed whether or not anyone queries; the replica consumes Dataverse storage capacity; and the link identity needs Dataverse System Administrator — a materially bigger IT grant that needs its own approval conversation (IT package item F, deliberately never submitted).

6 · Power Platform dataflows — copy

Not chosen

Hours setup · $0 Azure incremental (license-covered)

Low-code Power Query authoring; no Azure resources for Dataverse-destination flows.

Limits: it's an ETL surface, not a query endpoint — external code can't reach internal storage (BYO-ADLS needed); ≤48 refreshes/day, ~500 rows/s; source reads count against the same live API limits; author needs a Power Apps/BI license.

7 · Azure Data Factory (Dataverse connector) — copy

Not chosen

~1 day setup (+ watermark logic) · $5–50/month + sink cost

Copy to any sink — an ADF-fed Azure SQL DB would give the app a fully-owned transactional + analytical store.

Limits: you own schema drift, deletes, and incremental watermarks; extraction consumes the same throttled Dataverse API and competes with live users during runs; freshness is whatever the trigger cadence is.

Dead paths — do not build on these

  • Data Export Service (→ Azure SQL) — end-of-life Nov 2022
  • Export to Data Lake (F&O add-in) — decommissioning began Mar 2025
  • OData v2 Organization Data Service — removed; the platform returns OrganizationDataServiceDeprecatedError
  • 2011 SOAP endpoint — deprecated, no Node story at all
  • BYOD (F&O) — no EOL date, but Microsoft steers to Synapse/Fabric Link
  • Synapse Link "in-place update" CSV mode — documented as legacy; use append-only or Delta

All still appear in stale blog posts. If a tutorial mentions one, close the tab.

When would the answer change? The rubric

The research scored nine criteria against four synthetic table configurations (A–D). Match a real schema to the nearest configuration to see which criteria trip. This project's data resembles configuration A — which is why live-only won.

ConfigShapeVerdictThe criterion that decides it
A Reference mesh, <2k rows Branch-indifferent Nothing trips. Live wins only on cost ($0) and setup (<1 day). This is the floor case — and this project.
B Transactional core, 1.2M OrderLine Hybrid Global KPIs ("revenue by month, all time") hard-error on the 50k cap → copy those; column security + filtered per-account views keep point reads live.
C Event stream, 8M rows/yr, elastic table Copy-only for analytics 160× over the aggregate cap; elastic tables never appear in TDS; ingest velocity swamps the shared bucket.
D Hierarchy & documents, 400k BomLine Hybrid — forced both ways Hierarchy Under/Above operators exist only live (FetchXML); recursion (BOM explosion) exists only in a copy; files never export through Synapse Link, so documents are live-only regardless.

The hybrid pattern — a first-class outcome, not a compromise

Worth knowing even though it wasn't needed: if the tripwire ever fires, this is the shape the architecture grows into, and the single BFF is what makes it cheap.

WorkloadStoreWhy
Point lookups, filtered lists under the caps, hierarchy traversals, anything under column security Live (Web API)Caps don't trip; security enforced per query; hierarchy operators only exist here
Global KPIs, trends, any group-by that can touch ≥50k rows Copy (Synapse SQL)No caps, no throttle contact
Files and images Live — alwaysThey don't export through Synapse Link at all

The frontend never knows which store answered — both sit behind the same /api. The incremental cost over copy-only is near zero because the live leg's S2S setup is needed for file fetches anyway.
