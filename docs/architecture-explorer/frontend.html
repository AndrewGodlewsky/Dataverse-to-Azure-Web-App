Layer · Frontend & charting · ADR-0005

The charting choice the whole project hangs on

Custom cross-filtering is why this project exists as custom code at all — it's the requirement that disqualified Power BI at framing time. So the chart library wasn't picked on developer comfort; it was picked on which one carries that requirement natively.

The founding requirement Click a category bar → the KPIs and the revenue line filter to match. That interaction — bespoke cross-chart filtering — is outside Power BI's canned visual surface, which is why Power BI appears nowhere else in the option atlas. It's already working in the built app.

Decision — ADR-0005 (Accepted, medium confidence) Vite-built React SPA + Express BFF (same container, per ADR-0004) + Apache ECharts via echarts-for-react, imported modularly (echarts/core). Cross-filtering uses ECharts' native event/action machinery — on(), dispatchAction(), connect() — rather than hand-rolled React state. Accepted tradeoff: chart definitions live in ECharts option objects, the least React-ish API of the field, and the largest bundle.

The three stack combos

A · Vite + Express + ECharts — the interactivity-ceiling play

Chosen

Every shape native, canvas headroom for drill-downs, cross-filtering in the box; Express gives the cache/429 layer full freedom. Fits week-1 comfortably.

Cost: the options-object API and bundle management. In the built app the client bundle landed at ~776 kB pre-gzip / 260 kB gzipped — that's ECharts, fine for an internal tool; manualChunks if it ever matters.

B · Vite + Express + Recharts — the dev-speed play

Not chosen

Fastest of the three to build; lowest learning curve, JSX-composable.

Why it lost: the tree-diagram gap means rendering org/BOM views as an expandable list or pulling ECharts in for just that view (doubling the bundle on that page) — and cross-filtering is manual state exactly where the project needs it strongest.

C · Next.js standalone + visx (+ Chart.js) — the bespoke-UX play

Not chosen

No ceiling on novel linked visualizations; clean single-artifact Docker image via output: 'standalone'.

Why it lost: charts are client components anyway, so SSR buys nothing here; server/client boundaries and build-time file tracing are new failure modes; and visx-everything likely exceeds the week.

Why the BFF is non-negotiable

Tempting simplification: skip Express, let the React app call Dataverse directly. Three independent reasons it can never work on the live branch:

1 · The credential is confidential

The S2S credential is a confidential-client secret (later a managed-identity assertion). It cannot ship in browser JavaScript, full stop.

2 · One throttle bucket for everyone

All viewers share the app user's single 6,000-req/5-min bucket. Only a server can collapse N viewers into one cached upstream request and centrally honor Retry-After.

3 · Paging shouldn't reach the browser

The Web API returns 5,000 rows/page with no $skip — the @odata.nextLink loop belongs server-side, not in every client.

On a copy branch the same BFF simply points at the copy store instead — the browser can't query Azure SQL or a data lake either. The BFF survives every fork in the atlas.

Build fact worth keeping Chart colors come from CSS custom properties in client/src/styles.css (light and dark), read at render time via getComputedStyle in client/src/EChart.jsx. Don't hardcode hex values in chart options — the palette was validated in both themes.
