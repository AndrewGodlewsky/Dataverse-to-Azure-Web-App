One image, one registry, a ladder of deploy options

The frame — container image → registry → Azure Web App — was fixed at project framing. Inside it, the real choices are the image shape, how the app authenticates to the registry, which tiers to pay for, and how much CI/CD ceremony to adopt. The stance throughout: structural choices got an ADR; tier and CI/CD rung stayed deliberately reversible.

Decision — ADR-0004 (Accepted, high confidence) One multi-stage Dockerfile: stage 1 builds the Vite bundle, stage 2 is a slim node:22-alpine image running Express, serving /api and the static build on the port named in WEBSITES_PORT. The image lives in ACR Basic; the Web App pulls it with its managed identity holding AcrPull (acrUseManagedIdentityCreds=true). Plan tier and CI/CD rung are deliberately not part of the record — both are reversible operational settings.

Image shape — why one image and not two

ACR Basicpulled by the Web App's managed identity (AcrPull)

App Service custom containers expose exactly one HTTP port — a single image that serves both the API and the static frontend is the shape the platform wants. It also means one deploy unit, one TLS endpoint, and no CORS anywhere. The alternative (separate nginx + Node images as two apps or sidecars) buys independent release cadences at the price of CORS, double management, and more cost — unjustified for an internal tool where frontend and BFF have no independent-release pressure. The accepted tradeoff: a frontend-only tweak ships a full image.

Registry pull auth — the one with a wrong answer

OptionCostAssessment
Managed identity + AcrPull role Chosen $0 No credentials stored anywhere; the corporate default. Built-in Azure Policies exist specifically to deny the alternative. One check at setup: verify the role assignment wasn't policy-blocked, or pulls fail UNAUTHORIZED.
ACR admin account Anti-pattern $0 A single shared username/password with full push+pull, no RBAC, disabled by default, explicitly not recommended by Microsoft — expect tenant policy to forbid it. Its only legitimate niche is portal-driven deploys to ACI/ACA.

Also worth knowing: Azure Container Apps can run the identical image with scale-to-zero (~$0–5/month for idle-heavy internal use) if per-use cost ever dominates — at the price of cold starts and a different ops model. CI/CD — the effort ladder

The rungs are additive, not exclusive — starting manual and layering later is the plan, not a compromise. Current position: rung 1, by explicit choice (ADR-0004 keeps the rung out of the record so climbing needs no ceremony).

  1. Manual Current — by choice

    ~0 setup · $0/month · 5–10 min human effort per deploy · no new secrets

    az acr build --registry <acr> --image dashboard:latest . then restart the Web App. Nothing to configure; fine while iterating on infrastructure.

    No audit trail, and the app does not pull on its own — the restart is required every time.

  2. ACR webhook CD Best effort-to-payoff

    ~0.5–1 h setup · ~cents/month (a 5-min ACR Tasks build ≈ $0.03) · one command per deploy

    az acr build + an ACR webhook: pushing an image auto-restarts the app. No local Docker, no new secrets.

    Triggered by image push, not git push — no test/lint gate. Breaks if tenant policy disables App Service basic auth (the webhook 401s).

  3. GitHub Actions — publish profile Skippable

    ~1–2 h setup · $0 · deploy on git push · 1 GitHub secret (full publish-profile XML)

    Fastest real CI: tests + build + deploy on push.

    Requires SCM basic auth enabled — the same tenant-policy risk as rung 2, and the least secure posture of the ladder. If climbing this high, go one more rung.

  4. GitHub Actions — OIDC federated The standard end-state

    ~0.5 day setup · $0 · deploy on git push · 3 non-sensitive IDs, no long-lived secret

    Microsoft's recommended method. Needs an app registration + federated credential, or a user-assigned managed identity — the UAMI route sidesteps app-registration policy entirely (pure Azure RBAC).

    The federated subject claim must match the workflow trigger exactly — mismatches fail silently.

  5. Azure DevOps Pipelines Unjustified here

    ~1 day setup · free grant only after linking a billing subscription

    Its one trick: the AzureWebApp task works even with basic auth disabled, and ADO environments/gates exist if compliance demands them.

    The repo is on GitHub — ADO means a second system for zero functional gain.

Work-tenant blockers to check before climbing Four policies cut across the ladder: app-registration creation disabled (blocks rung 4's registration route — the UAMI route avoids it) · Conditional Access on workload identities (can block service-principal sign-ins from GitHub's runners; managed identities are exempt) · basic auth disabled on App Service (kills rung 2's webhook and rung 3 entirely) · ACR admin account disabled (forces the managed-identity path — the chosen default anyway). Check them before committing to a rung, not after it 401s.
