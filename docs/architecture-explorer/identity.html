Layer · Identity · ADR-0002 & ADR-0003

Two auth problems, solved separately

The server needs an identity to read Dataverse (server-to-server), and viewers need to be gated at the front door (browser-to-app). They're independent decisions with independent option fields — and both landed on the smallest thing that works.

Problem 1 — how the BFF authenticates to Dataverse

The shared foundation (identical in every variation) An unlicensed Dataverse application user carrying a custom read-only Dashboard Reader security role, and the BFF requesting tokens for scope https://<org>.crm.dynamics.com/.default. What varies is which identity object the application user is bound to and how the token is obtained. Token acquisition is isolated in one module (getToken() in server/dataverse.js) — swapping variations is a config change plus ~10 lines, never a rebuild.

Decision — ADR-0002 (Accepted, high confidence) Stage it: start with V1 (client secret) for day-1 connectivity from a laptop, finish with V2 (federated identity credential) once the Web App's user-assigned managed identity exists, then delete the secret. The application user never changes, so the upgrade is zero-rework. V3 was rejected because it forecloses per-user auth permanently.

The handoff doc schedules the upgrade as part of Azure provisioning specifically to prevent this.

V1 · Client secret

Stage 1 — in use now

The documented mainstream S2S path: an app registration holds a secret; the BFF trades it for tokens via msal-node client-credentials.

  1. BFF → Entra — sends client_id + client_secret (client-credentials grant); secret comes from an app setting or Key Vault reference
  2. Entra → BFF — returns an access token carrying the app registration's identity
  3. BFF → Dataverse — GET /api/data/v9.2/… with the bearer token; rows authorized through the application user's role

Why it leads: works before any Azure resource exists — first Dataverse query can run day 1 from a laptop, and local dev is identical to prod.

Costs: the secret expires (value shown once at creation), rotation is on you, leakage is the risk Key Vault mitigates. All temporary by design.

V2 · Federated identity credential (FIC)

Stage 2 — the end state

The app registration stays (governable, can hold future permissions) but no secret exists: the registration trusts the Web App's user-assigned managed identity via a federated credential with audience api://AzureADTokenExchange.

  1. BFF → MI endpoint — asks App Service for a managed-identity token (audience api://AzureADTokenExchange)
  2. BFF → Entra — presents that MI token as a client assertion for the app registration
  3. Entra → BFF — returns an access token carrying the app registration's identity (same identity as V1)
  4. BFF → Dataverse — same bearer call as V1; the application user binding is untouched

Why it's the end state: nothing expires, nothing is stored, and the registration survives — so per-user (on-behalf-of) auth stays possible later.

Costs: can't exist until the managed identity does; local dev needs a separate dev credential; FIC changes propagate in minutes — handle the transient AADSTS70021 with a retry.

V3 · Managed identity direct

Rejected

No app registration at all — the managed identity's Application ID is entered directly as the Dataverse application user. The shortest code of the three and the smallest possible IT footprint (no Entra directory operation).

  1. BFF → MI endpoint — asks for a token scoped straight to https://<org>.crm.dynamics.com/.default
  2. BFF → Dataverse — bearer call; the application user is the managed identity

Why it lost: a laptop has no managed identity, so local dev needs a second identity with its own separate application user, role-synced forever; and with no app registration there's nowhere to hang delegated permissions — a dead end if per-user auth ever returns. Different binding, so it's not upgradeable from V1 either.

Problem 2 — how viewers get in

Decision — ADR-0003 (Accepted, high confidence) App Service Easy Auth with the Entra provider gates the entire site; the auto-created enterprise application is set to Assignment required and a dedicated viewer group is assigned. Granting access = adding a person to the group. The app contains zero sign-in code; identity arrives as unspoofable X-MS-CLIENT-PRINCIPAL* headers, read for display/telemetry only. Everyone with access sees everything — user-confirmed, and it's what keeps the BFF cache shared and effective.

OptionSetupStrengthsWhy chosen / not
Easy Auth + Assignment required + viewer group Chosen Minutes Zero auth code; platform gates before the container; membership managed in one Entra group Fits the everyone-sees-everything model exactly; sign-in UX is Microsoft's — accepted
Easy Auth, any tenant user Minutes Simplest possible The whole tenant could open the dashboard — contradicts deliberate, person-by-person access granting
In-app MSAL (+ optional per-user OBO) Days Full sign-in UX control; Dataverse's own row/column security per viewer; each viewer gets their own throttle bucket Days of plumbing buying nothing under the no-restrictions model — and viewer-specific responses would defeat the shared cache ADR-0001 depends on
No auth — — Dataverse-derived data on an open URL

A middle path kept in reserve If per-viewer data ever becomes a requirement: Easy Auth with the token store enabled already hands the container the user's access token (X-MS-TOKEN-AAD-ACCESS-TOKEN). With the delegated-permission chain set up, the BFF can run on-behalf-of flows from that header with no SPA-side MSAL at all. That change would revisit ADR-0003 — likely alongside the OBO door that ADR-0002's surviving app registration deliberately keeps open.
