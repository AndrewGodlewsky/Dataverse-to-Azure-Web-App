Both paths end at the same place — an unlicensed application user inside a Dataverse environment, carrying a custom read-only role. Everything that differs is upstream of that: which identity object the app user is bound to, and how your Node process proves it is that object.

Framing

"Service account" is the wrong noun — and that's good news

In most systems a service account is a real user account with a password that nobody logs into interactively. Dataverse supports that, and Microsoft tells you not to do it: "While you could achieve these scenarios by using credentials for an ordinary user, that user account needs a paid license. Don't use this approach."

The supported object is an application user — a Dataverse principal bound to an Entra identity rather than to a human. It has three properties that make it the right thing:

  • It is unlicensed. It consumes no paid seat, ever.
  • It has no password. There is nothing to phish, and nothing a person can accidentally reuse.
  • It carries a security role like any other user, so Dataverse's normal authorization model applies unchanged — table privileges, business unit scope, column security.

So when this report says "the two ways," it means two ways of answering one question: what Entra object is the application user bound to, and how does your Web App prove it is that object? Everything else is shared.

Terminology you'll hit in the portal

Microsoft's docs use "service principal," "application user," and "S2S authentication" for overlapping parts of this. Roughly: the service principal is the Entra-side identity, the application user is its Dataverse-side seat, and S2S is the flow between them. Only the application user grants data access — Entra API permissions do not.

Shared

The foundation you build either way

Four links in a chain. Three of them are identical whichever path you take — only the first box changes shape. Build them in this order, because each one needs the previous one's identifier.

What to create, in order

  1. An Entra identityAn app registration (Way A) or a user-assigned managed identity (Way B). This is §4 and §5.
  2. A custom security rolePower Platform admin center → environment → Settings → Users + permissions → Security roles. Copying App Opener is a good starting point because it already carries the documented minimum privileges. Grant Read only, on exactly the tables the dashboard needs.
  3. The application userSettings → Users + permissions → Application users → + New app user → + Add an app. Pick a business unit, set an email address, assign the role from step 2.
  4. A column security profile — only if you need oneIf any dashboard column is secured, a valid security role is not enough: the application user must also be added to a column security profile with Read = Allowed, or those columns come back masked.
Three constraints that bite during setup

A default role will be rejected. The docs are explicit: "The application user cannot be associated with one of the default Dataverse security roles. You must create a custom security role."

One application user per registered app, per environment. If you want separate dev and prod identities against the same environment, that is two Entra objects and two application users — not one reused.

Enterprise applications don't appear in the picker. Only Entra app registrations are listed. For a managed identity you must search by its Application ID; it will not surface by name.

The fork

What actually differs

Way B has two shapes, because "use a managed identity" can mean either the MI is the identity Dataverse knows about (B1) or the MI is how an app registration proves itself (B2). They look similar from the code and identical from Dataverse, but their Entra footprint and their future options differ sharply.

Way A

App registration + client secret

The documented mainstream path, and the only one that works before any Azure resource exists. An app registration holds a secret; your process trades the secret for a token via the OAuth client credentials grant.

Setup

  1. Register the appEntra ID → App registrations → New registration. Supported account types: Accounts in this organizational directory only. No redirect URI — this is a daemon client.
  2. Add no API permissionsGenuinely none. Microsoft: "If your app uses Server-to-Server (S2S) authentication, you don't need to complete this step." The user_impersonation permission is for delegated per-user access only.
  3. Create the secretCertificates & secrets → New client secret. Choose an expiry you will actually track. Copy the value now — it is displayed exactly once, and there is no way to read it back.
  4. Record three valuesApplication (client) ID, Directory (tenant) ID, and the secret value.
  5. Bind and authorizeCreate the application user against this registration, assign the custom role — §2, steps 2–3.
  6. Store the secret properlyAn App Service application setting, or better a Key Vault reference. Never in the image, never in source control.
server/dataverse.js — Way A token acquisition 
// @azure/msal-node v3 uses named ESM exports — not a default import.
import { ConfidentialClientApplication } from "@azure/msal-node";

const cca = new ConfidentialClientApplication({
  auth: {
    clientId:     process.env.CLIENT_ID,
    authority:    `https://login.microsoftonline.com/${process.env.TENANT_ID}`,
    clientSecret: process.env.CLIENT_SECRET,
  },
});

const scope = `${process.env.DATAVERSE_URL}/.default`;

// MSAL caches the app token internally and reuses it until near expiry,
// so calling this per request is fine — but keep `cca` module-level.
export async function getToken() {
  const r = await cca.acquireTokenByClientCredential({ scopes: [scope] });
  return r.accessToken;
}
Way A's real cost

The secret expires. Whatever expiry you pick, something must remind a human before that date — a calendar entry, an Entra expiry alert, anything. A dashboard that silently stops loading eighteen months from now, with an AADSTS7000222 nobody recognises, is the standard failure mode of this path.

Way B

Managed identity — two shapes

A managed identity is an Entra identity that Azure creates, assigns to a resource, and rotates the credentials for. Your code never sees a secret; it asks a local endpoint on the App Service host for a token. Microsoft's stated preference is blunt: "use the most secure authentication flow available… such as managed identities."

Prefer a user-assigned managed identity over system-assigned for both shapes. It exists independently of the Web App, so you can provision it and wire up Dataverse before the app is deployed; it survives the app being deleted and recreated; and B2 requires it outright.

B1 — the managed identity is the application user

The shortest possible version. No app registration exists at all; you paste the MI's Application ID straight into Power Platform admin center. The docs support this explicitly: "In addition to entering the Application Name or Application ID, you can also enter an Azure Managed Identity Application ID. For Managed Identity, do not enter the Managed Identity Application Name, use the Managed Identity Application ID instead."

server/dataverse.js — Way B1 token acquisition 
import { ManagedIdentityCredential } from "@azure/identity";

// Pass the client ID explicitly. Omit it and the SDK asks for a
// SYSTEM-assigned identity, which may not exist — see §9.
const cred = new ManagedIdentityCredential({
  clientId: process.env.MI_CLIENT_ID,
});

const scope = `${process.env.DATAVERSE_URL}/.default`;

export async function getToken() {
  const t = await cred.getToken([scope]);
  return t.token;
}

B2 — the app registration trusts the managed identity

The federated identity credential (FIC) route, also called workload identity federation. You keep a normal app registration — governable, permission-holding, familiar to IT — but it holds no secret. Instead it declares that it trusts a specific user-assigned managed identity. At runtime the app gets an MI token with audience api://AzureADTokenExchange and presents it to Entra as a client assertion.

Setup

  1. Create the user-assigned managed identityA standalone Azure resource. Note both its Client ID and its Object (principal) ID — you need each in a different place. See §6.
  2. Assign it to the Web AppWeb App → Identity → User assigned → Add.
  3. Add the federated credentialOn the app registration: Certificates & secrets → Federated credentials → Add credential → scenario Managed Identity → select the UAMI. Issuer is prefilled as https://login.microsoftonline.com/{tenantID}/v2.0; audience must be api://AzureADTokenExchange.
  4. Wait a few minutes before testingNot optional. Propagation is real and produces a confusing error — §10.
  5. Bind and authorizeThe application user is bound to the app registration, exactly as in Way A. If you are migrating from Way A, this already exists and needs no change.
  6. Delete the secretOnly after the new path is verified working in the deployed app.
server/dataverse.js — Way B2 token acquisition 
// No msal-node needed here — @azure/identity wraps the whole exchange.
import { ManagedIdentityCredential, ClientAssertionCredential } from "@azure/identity";

const mi = new ManagedIdentityCredential({ clientId: process.env.MI_CLIENT_ID });

const cred = new ClientAssertionCredential(
  process.env.TENANT_ID,
  process.env.CLIENT_ID,                     // the APP REGISTRATION's client ID
  async () => (await mi.getToken(["api://AzureADTokenExchange/.default"])).token
);

const scope = `${process.env.DATAVERSE_URL}/.default`;

export async function getToken() {
  const t = await cred.getToken([scope]);
  return t.token;
}
Non-global clouds

The audience changes: api://AzureADTokenExchangeUSGov for US Government, api://AzureADTokenExchangeChina for Entra ID China operated by 21Vianet. It must match on both the FIC and in code.

The trap

One identity, two GUIDs

This is the single most expensive mistake in this space, and it is worth internalising before you touch a portal. A user-assigned managed identity carries two different GUIDs, and the two Way-B shapes need different ones. They are both 36-character GUIDs sitting on the same overview blade, a few pixels apart.

Why this costs a day, not five minutes

Microsoft documents the behaviour plainly: "If you accidentally add the incorrect external workload information in the subject setting the federated identity credential is created successfully without error. The error does not become apparent until the token exchange fails."

So a wrong subject looks exactly like a correct one in the portal. It then produces AADSTS70021 at runtime — which is also what a not-yet-propagated correct credential produces. You cannot tell the two apart from the error alone, which is why people wait, retry, wait longer, and only much later re-read the GUID.

The five-second check

Before debugging anything else, compare the two directly:

az identity show -g <rg> -n <mi> --query "{client:clientId, object:principalId}"
az ad app federated-credential list --id <appId> --query "[].subject"

The second must equal object, not client. If it matches client, that is your bug and no amount of waiting will fix it.

Choose A ifYou need data today, IT turnaround is slow, or you want local dev and production to behave identically. It is also the correct first step even when B2 is the destination.
Choose B1 ifApp registrations are politically expensive in your tenant, and you are confident per-user access will never be needed. The zero-directory-objects footprint is genuinely the smallest possible ask.

The honest summary

B1 and B2 are not really "two options against A" — they are one security posture with two governance shapes. If your organization already thinks in app registrations, B2. If it does not, B1. The security difference between them is nil; the flexibility difference is large and only matters if requirements change.

Migration

The staged path: start A, finish B2

Because A and B2 bind the same app registration, the application user survives the move untouched. That makes the sequence below a config change plus one function body — not a rebuild, and not a Dataverse operation.

Keep the swap surface small

All three code samples in this report export the same one-line contract: getToken() → string. If your query, retry, paging and caching machinery sits behind that boundary, migrating between paths never touches it. This is worth enforcing on day one even if you never migrate — it is also what makes the paths independently testable.

Field notes

Tips & tricks

Identity and credentials

Pass the client ID explicitly for user-assigned identities
If you omit every ID parameter, the token endpoint tries the system-assigned identity — "which might or might not exist." On a Web App with only a user-assigned identity this fails in a way that reads like a permissions problem rather than a wiring problem. Always pass clientId.
Grant no API permissions for S2S, and don't be talked out of it
The federated-credential documentation carries a generic prerequisite about the app needing "access granted to Microsoft Entra protected resources… through API permissions." That is boilerplate for the general FIC case and does not apply to Dataverse S2S, where the application user and its security role carry all authorization. Adding user_impersonation "just in case" invites a consent conversation you do not need.
Creating a federated credential needs a privileged Entra role
Application Administrator, Application Developer, Cloud Application Administrator, or Application Owner. Name this in the IT request up front — otherwise the ticket bounces once, which on a typical enterprise turnaround costs more calendar time than the whole rest of the setup.
Twenty federated credentials per object, maximum
Applies to both app registrations and user-assigned managed identities. Not a constraint for one dashboard; very much one if you are planning a per-environment credential strategy across a lot of workloads.
Same tenant, both sides
The app registration and the managed identity must live in the same tenant, even when the target resource is elsewhere. Cross-tenant FIC is supported; cross-cloud is not.
Key Vault references, and the identity they use
If you keep a secret (Way A), an App Service Key Vault reference gets it out of app settings with no code change. By default the reference resolves using the app's system-assigned identity. To use a user-assigned one, set keyVaultReferenceIdentity to its resource ID — a common gotcha on apps that have only a user-assigned identity.

Tokens at runtime

Don't build a token cache — but do keep the credential object alive
MSAL and @azure/identity both cache app tokens internally and refresh near expiry. Rolling your own cache is redundant and gets the refresh edge case wrong. What does matter: construct the credential once at module scope. Constructing it per request throws the cache away and hammers the token endpoint.
Retry token acquisition on the federated path — always, not just at first
Microsoft's guidance on FIC propagation is specific: "Retries should be done for every request even after a token was successfully obtained." Replication across authorization-service nodes is eventual, so a previously-working exchange can fail transiently.
The scope is the org URI, not a fixed resource string
https://<org>.crm.dynamics.com/.default, with your organization's own hostname. Getting the region suffix wrong (crm4, crm11…) yields a token that is valid but rejected downstream — an easy misread as an authorization failure.
@azure/msal-node v3 uses named ESM exports
import { ConfidentialClientApplication } from "@azure/msal-node" — a default import silently yields undefined and fails at construction, not at import.

Querying Dataverse without tripping over it

Always $select
Omitting it returns every column on every row. On a wide table this is the difference between a fast dashboard and a throttled one, and it is the single cheapest performance fix available.
Page with Prefer: odata.maxpagesize, never $skip
Dataverse does not support $skip, so the usual $top/$skip pattern simply cannot be built. Use the header (max 5,000; larger values are ignored) and follow @odata.nextLink verbatim — don't modify it, don't append query options, and keep the same page size on every subsequent request.
$top and maxpagesize are mutually exclusive in practice
If you send both, $top is silently ignored. Use $top to cap a result set, maxpagesize to page through one — never both.
Order deterministically or paging lies to you
Without a deterministic sort, "page 2" is not a stable concept — records can repeat or vanish between pages. Include something unique (or a unique combination) in $orderby. Also: paging works forward. Re-fetching an earlier page can legitimately return different rows.
Formatted values come from an annotation, not a column
Prefer: odata.include-annotations="OData.Community.Display.V1.FormattedValue" gets you choice labels, currency symbols, lookup display names and user-timezone dates as <property>@OData.Community.Display.V1.FormattedValue. Without it you get raw option-set integers and have to re-implement the label mapping yourself — a classic source of dashboards that drift out of sync with the data model.
Secured columns return masked values even with a correct role
Column-level security is evaluated separately from the security role. If the app user is not in a column security profile granting Read on those columns, the dashboard sees masked values — not an error. Silent wrong data is worse than a failure, so check this explicitly if any dashboard field is sensitive.

Throttling

Your app is one bucket, shared by every viewer
Service protection limits are evaluated per user in a 5-minute sliding window. With an application user, all your viewers share a single allocation — so throughput scales with the number of viewers but the limit does not. This is the main architectural argument for caching at the BFF, and the main reason per-user on-behalf-of access is sometimes chosen instead.
Honour Retry-After, and back off gently
A 429 carries a Retry-After in seconds. Microsoft's advice is counter-intuitive but important: if you keep pushing after the first 429, the interval gets longer. Aim for a consistent rate, start low, increase gradually, and let the server set the ceiling.
The rate-limit headers are for debugging only
x-ms-ratelimit-burst-remaining-xrm-requests and x-ms-ratelimit-time-remaining-xrm-requests tell you where you stand, but the docs say plainly: don't drive request pacing from them. They reset when you land on a different server.

Local development

Managed identity does not exist on a laptop
This is the structural weakness of both B shapes and there is no way around it. Way A is uniquely comfortable here because dev and prod are the same mechanism.
B2's local story is much better than B1's
On B2, dev can use a client secret against the same app registration — same application user, same role, same permissions. On B1 there is no registration to fall back to, so dev needs a separate identity with its own application user, and those two must be kept role-synchronised for the life of the app. That ongoing tax is B1's real cost, and it is easy to miss when comparing them on paper.
A mock mode pays for itself immediately
Being able to develop and test the whole dashboard with no credential at all removes Dataverse provisioning from the critical path entirely — you can build, style and screenshot the app while the IT ticket is still open.

Diagnosis

Error decoder

Most failures on these paths produce one of a small set of errors, and several of them point somewhere other than where they seem to.

ErrorWhat it usually meansFirst thing to check
AADSTS70021 No matching federated identity record. Ambiguous — either the credential hasn't propagated yet, or the subject is wrong. Compare the FIC subject against the MI's Object (principal) ID, not its Client ID (§6). Only if that matches is waiting the answer.
AADSTS700213 No matching record for the presented assertion subject specifically. Same check, but this variant rules out the issuer — it is the subject.
AADSTS700211 No matching record for the assertion issuer. Issuer must be exactly https://login.microsoftonline.com/{tenantID}/v2.0. Leading or trailing whitespace blocks the exchange.
AADSTS70025 The client application has no federated identity credentials configured at all. You added the FIC to the wrong object — check whether it landed on the managed identity instead of the app registration.
AADSTS700223 Workload identity federation is constrained or disabled tenant-wide. A tenant policy decision, not a config error. Way B2 may be unavailable to you; B1 or A are the fallbacks. Treat this as a security control and ask before working around it.
401 from Dataverse Token acquired fine, but Dataverse doesn't recognise the caller. The application user is missing, bound to a different object than the token's identity, or in a different environment than the one you're calling.
403 from Dataverse Recognised, but not authorized. The security role is missing, has no Read on that table, or is scoped below organization level. This is a role problem, never a token problem.
429 Service protection limit. Honour Retry-After. If it's persistent rather than bursty, the fix is caching or fewer/wider queries, not faster retries.
Masked values
(no error)		 Column-level security. Add the application user to a column security profile with Read = Allowed.
Empty result
(no error)		 Usually business-unit scope on the role, or a filter matching nothing. Run WhoAmI first to confirm identity, then re-run the query with no $filter.

Verification

Smoke tests — prove each link separately

The chain in Fig. 1 has four links, and a failure anywhere produces roughly the same symptom: no data. Test them individually and in order, and you never have to guess which one broke.

1 · can I get a token at all? 
# Way A — from anywhere
curl -s -X POST "https://login.microsoftonline.com/$TENANT_ID/oauth2/v2.0/token" \
  -d "client_id=$CLIENT_ID" \
  -d "client_secret=$CLIENT_SECRET" \
  -d "scope=$DATAVERSE_URL/.default" \
  -d "grant_type=client_credentials"

# Way B — from inside the Web App only (SSH / Kudu console)
curl -s "$IDENTITY_ENDPOINT?resource=$DATAVERSE_URL&api-version=2019-08-01&client_id=$MI_CLIENT_ID" \
  -H "X-IDENTITY-HEADER: $IDENTITY_HEADER"
2 · does Dataverse know who I am? 
curl -s "$DATAVERSE_URL/api/data/v9.2/WhoAmI" \
  -H "Authorization: Bearer $TOKEN" \
  -H "OData-MaxVersion: 4.0" -H "OData-Version: 4.0" -H "Accept: application/json"

# 200 + a UserId  → the application user exists and is bound correctly.
# 401            → binding problem: wrong object, or wrong environment.
3 · can I read the tables I need? 
curl -s "$DATAVERSE_URL/api/data/v9.2/accounts?\$select=name&\$top=1" \
  -H "Authorization: Bearer $TOKEN" \
  -H "OData-MaxVersion: 4.0" -H "OData-Version: 4.0" -H "Accept: application/json"

# 403 here but 200 on WhoAmI → the role is the problem, not the identity.
4 · is the federated credential wired to the right GUID? 
az identity show -g "$RG" -n "$MI_NAME" --query "{client:clientId, object:principalId}"
az ad app federated-credential list --id "$APP_ID" --query "[].{n:name, sub:subject, aud:audiences[0]}"

# sub must equal `object`. If it equals `client`, that is the bug. (§6)
Why WhoAmI is the right second test

It needs a valid token and a valid application user, but essentially no privileges — so it cleanly separates "who am I" from "what may I read." A 200 on WhoAmI followed by a 403 on a table is an unambiguous signal that identity is fine and the security role is not, which is a completely different ticket to a completely different person.

Anti-patterns

Things not to do

Don't authenticate as a licensed human user
Username and password against a real account — the Office365 auth type, or ROPC — is deprecated, consumes a paid license, breaks under MFA and conditional access, and makes every audit trail read as that person. Microsoft says not to. There is no version of this that ages well.
Don't give the application user System Administrator
It is the fastest way to make a 403 go away and the slowest to undo. A read-only dashboard needs Read on a handful of tables. Granting admin to a non-interactive identity with a stored credential converts a small credential leak into a full environment compromise.
Don't put the secret in the image or in source control
A container image is not a secret store — anyone who can pull it can read it, and it persists in registry history after you "fix" it. App settings or a Key Vault reference, always.
Don't confuse "Power Platform managed identity" with this
That feature is about Dataverse plug-ins calling out to Azure — the opposite direction, with its own managedidentity table records, FIC subject formats and plug-in signing requirements. Searching for "Dataverse managed identity" lands there constantly. It is not this, and none of its setup steps apply.
Don't let the app registration accumulate permissions "for later"
An S2S registration for a read-only dashboard should have zero API permissions for its whole life. Every permission added is a consent grant that outlives the reason for it.
Don't route around a blocked federation
If AADSTS700223 says workload identity federation is constrained tenant-wide, that is a deliberate policy someone set. Use Way A or B1 and raise it — don't look for a way to bypass the constraint.
